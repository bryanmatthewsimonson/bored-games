# Phases 2e and 3: relay transport and the web client, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a static web app in which real people log in with a NOSTR key, create or join a Chain Reaction table and play a whole asynchronous game over NOSTR relays. It also includes a local development relay and an end-to-end browser test.

**Architecture:**
- `packages/relay` is a small NIP-01 relay pool over an injected `WebSocket` constructor. It is not pure (it does network I/O), but its logic is tested against a fake socket.
- `tools/dev-relay` is a minimal in-memory NIP-01 relay server for local play and end-to-end tests.
- `apps/web` uses Preact and Signals on Vite (D014, option B, ruled by the controller while the owner was away; see D028). It has three layers:
  - an identity layer: NIP-07, or a local key per profile
  - controllers that bind `RelayPool` to `GameSession` and `foldLobby`, and run the automatic duties
  - screens: Home, Table and Game, with the Chain Reaction board
- Everything is client-side and static, with relative asset paths (Capacitor-ready).

**Tech stack:**
- New dependencies, each justified in D028: `preact`, `@preact/signals`, `@preact/preset-vite` (if it works with Vite 8; otherwise Vite's built-in JSX transform), and `ws` (dev only, for the dev relay).
- Playwright from the container (`/opt/pw-browsers`), already used by Vitest's environment.

**Spec:** `docs/PROTOCOL.md` §9 (relays); the PLAN Phase 3 acceptance criteria; `docs/games/chain-reaction/RULES.md` for what the UI must let a player do; the 2d session API (`docs/superpowers/plans/2026-10-01-phase-2d-session.md`, Shared interfaces).

## Global constraints
- **Branding.** No reference-game names. User-facing game names come from `CHAIN_REACTION_THEME` only, and the platform name from `BRAND`. The repo branding guard must cover `apps/web/src`.
- **Accessibility.** Chains are distinguished by label and pattern, never by color alone. Every control is reachable by keyboard.
- **Layout.** Phone portrait (360 px), tablet and desktop.
- **Identity.**
  - NIP-07 (`window.nostr`) when present, otherwise a local secret key in `localStorage`, namespaced by a profile name taken from the URL query `?profile=<name>`. The default profile is `default`.
  - The local key can be shown (nsec) and exported. A warning says that it is stored in this browser.
  - Per-game secrets (`sessionSk`, `deckSecret`) live in `localStorage` under the same profile, keyed by table address.
- **Relays.**
  - Default list: `wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.nostr.band`.
  - In development (`import.meta.env.DEV`), `ws://localhost:7777` comes first.
  - The list is editable in Settings.
  - The table carries its relays (§4.1), and game events go to them.
- **Routes** are hash routes:
  - `#/` Home
  - `#/t/<creatorHex>/<tableId>` a Table (lobby)
  - `#/g/<rootId>` a Game
- **Automatic duties.** While the Game screen is open, the client performs its `shuffle`, `deal`, `secret` and `attest` duties, and claims timeouts once eligible. Only `decide` needs the player. Long proofs show a "working…" state.
- **Checks.** `pnpm check` (typecheck, lint and test) covers `apps/web`, `packages/relay` and `tools/dev-relay`. `pnpm --filter @bored-games/web build` produces `apps/web/dist`.

## Review focus
1. **A tab reopened mid-game** must rebuild from relays and local secrets and carry on. Nothing may live only in memory. (Tasks 3 and 6.)
2. **Relay failures:** one relay down, a relay rejecting an event, or a relay delivering duplicates. The pool must still publish to the others, deduplicate, and never re-sign. (Task 1.)
3. **Two tabs with different profiles in one browser** must act as different players. (Tasks 2 and 6.)
4. **A player acting out of turn,** or clicking twice, must not publish an invalid or duplicate move. Disable the controls and build from the session's current head only. (Tasks 3 and 5.)
5. **Small screens.** The 12×9 board and the hand must stay usable at 360 px wide. (Task 5.)

### Task 1: `packages/relay`, a relay pool, and `tools/dev-relay`

**Files:**
- `packages/relay/{package.json,tsconfig*.json,src/pool.ts,src/index.ts,test/pool.test.ts}`
- `tools/dev-relay/{package.json,src/server.ts,test/dev-relay.test.ts}`
- Root `package.json` script `relay`
- `vitest.config.ts`
- `docs/DECISIONS.md`: D028, covering `ws` (dev only) and the frontend dependencies, which Task 2 adds

**Interfaces:**
- `class RelayPool` with `constructor(urls: string[], opts: { WebSocket: typeof WebSocket; backoffMs?: number[] })`.
  - `publish(ev: NostrEvent): Promise<{ url: string; ok: boolean; message: string }[]>`. It sends `["EVENT", ev]` to each relay and waits for `OK`, with a 10 s timeout per relay. If the socket is not open, it queues the event until the socket connects. It never mutates `ev`.
  - `subscribe(filters: Filter[], onEvent: (ev: NostrEvent, url: string) => void, onEose?: () => void): () => void`. It deduplicates by event id across relays and drops events that fail `verifyEvent`. On reconnect it resends the `REQ`.
  - `close()`.
  - `status(): { url: string; state: 'connecting' | 'open' | 'closed' }[]`.
- `type Filter = { ids?: string[]; kinds?: number[]; authors?: string[]; '#e'?: string[]; '#a'?: string[]; '#d'?: string[]; '#p'?: string[]; since?: number; limit?: number }`.
- The dev relay is started by `startDevRelay({ port }): Promise<{ url; close() }>`. It is an in-memory NIP-01 relay supporting `EVENT` (verify, store, `OK`), `REQ` (stored matches, then `EOSE`, then live events), `CLOSE`, and NIP-01 replaceable and addressable semantics for kinds 30000–39999 (keep the latest per `pubkey`, `kind` and `d`). `pnpm relay` runs it on port 7777.

**Steps:**
- [ ] **Step 1.** Write the pool tests with a fake WebSocket class. Cover:
  - publishing to 2 relays, where one returns `OK false`
  - queueing before open
  - deduplication across relays
  - dropping invalid events
  - resubscribing on reconnect
  - unsubscribe sending `CLOSE`

  Write the dev-relay tests with the real pool and Node's global `WebSocket`: publish, query, live delivery, and replacement of an addressable event.
- [ ] **Step 2.** Red, implement, green. Run `pnpm check`.
- [ ] **Step 3.** Commit "Add relay pool and dev relay".

### Task 2: The `apps/web` scaffold, identity and settings

**Files:**

- Tests: `apps/web/test/*.test.ts` (pure helpers, run in node)
- Root `package.json` scripts: `dev`, which runs `pnpm relay` and the Vite dev server together, with no new dependency (a small node script spawning both is fine), and `build:web`
- `tests/repo-guards.test.ts`: the branding scan covers `apps/web/src`

**Interfaces:**
- `interface Signer { pubkey: Hex; sign(t: EventTemplate): Promise<NostrEvent>; kind: 'nip07' | 'local' }`.
- `loadIdentity(profile: string, storage: Storage, rnd): Promise<Signer>`. It uses NIP-07 if `window.nostr` exists and the user chose it; otherwise it uses a local key.
- `profileFromLocation(loc): string`.
- `gameSecrets` storage: `saveSecrets(profile, tableAddress, {sessionSk, deckSecret})` and `loadSecrets(profile, tableAddress)`, stored as hex.
- `router`: a signal of the parsed hash route.
- `settings`: a signal of the relay list, persisted per profile.

The randomness source is `crypto.getRandomValues`, wrapped as `RandomBytes` in `src/random.ts`. Wall-clock time is `Math.floor(Date.now() / 1000)`, in `src/clock.ts`. These are the only impure entry points.

### Task 3: Controllers for the lobby and the game

**Files:**
- `apps/web/src/net.ts`: the singleton `RelayPool` from settings
- `apps/web/src/lobby-controller.ts`, `apps/web/src/game-controller.ts`
- `apps/web/test/controllers.test.ts`, which uses the dev relay in-process together with the real pool and sessions

**Interfaces:**
- `LobbyController`:
  - `openTables` signal: subscribes to kind 37450 with `status=open` for module `chain-reaction`, limited to recent tables.
  - `myTables` signal: tables I created or joined, with joins from `#a`.
  - `createTable({seats, deadline, invited, relays}) → address`. It signs the table and the creator's join, and saves the secrets.
  - `join(address)`: signs a join and saves the secrets.
  - `table(address)` signal: a `LobbyView`.
  - `start(address)`: the creator only, once the table is full. It signs the root, then republishes the table with `status: started`.
- `GameController(rootId)`:
  - It loads the table, joins and root, builds a `GameSession` with `me` from the saved secrets (or `null`, as a spectator), and subscribes to `#e` the root.
  - A `view` signal is updated after each `receive`.
  - `tick` runs every 30 s.
  - The duty loop runs one duty at a time:
    - build the event
    - publish it to the root relays plus my relays
    - receive it locally
  - `act(action)`: for the `decide` duty only. It guards against double submission while a publish is in flight.
  - `claimTimeout()`.
  - `status` signal: `'syncing' | 'working' | 'waiting' | 'your-turn' | 'done' | 'cancelled'`.
  - It never re-signs an event. It keeps the last built event and republishes the same one.

**Steps:**
- [ ] **Step 1.** Write the failing tests. Three controller pairs with different signers, all on one dev relay:
  - Create, join, join, start. Every pair sees the same root.
  - Every `GameController` reaches `'play'` without user input (the automatic shuffle and deal).
  - A controller rebuilt from scratch mid-game, with the same storage, reaches the same view.
- [ ] **Step 2.** Red, implement, green. Run `pnpm check`. Commit "Add lobby and game controllers".

### Task 5: The Game screen and the Chain Reaction board

**Files:** `apps/web/src/screens/game.tsx`, `apps/web/src/games/chain-reaction/{board.tsx,hand.tsx,panels.tsx,decisions.tsx,model.ts}`, `apps/web/test/cr-model.test.ts`.

**Model** (`model.ts`, pure):
- `boardCells(state)`: label, chain, pattern and whether the cell is the last placed tile.
- `handTiles(state, seat)`: each tile with its classification (playable, found, merge, dead, blocked) and a preview.
- `chainRows(state)`: name, label, size, price, safe flag, bank shares and my shares.
- `playerRows(state)`.
- `decisionFor(state, legal)`: maps the legal actions to a UI decision:
  - place: pick a tile
  - skip
  - found: pick a chain
  - survivor
  - order defuncts
  - dispose: sell / trade / keep amounts
  - endTurn: up to 3 buys, the discards of dead tiles, and the declare-end option

  It always submits an action that is in `legalActions()`; the dispose and buy forms match exactly against the legal list.
- `describeEvent`: one log line per module event.

**UI:**
- A 12×9 board with row letters A–I and columns 1–12.
- Chain cells show the chain label and pattern via CSS patterns.
- The hand shows the tiles, and hovering or focusing a tile previews where it lands.
- Side panels show chains and players: cash is public, and share counts are public.
- A decision area and a status bar: whose turn it is, "waiting for shares", the deadline countdown, and a claim-timeout button when eligible.
- An event log.
- Final results with the audit badge.
- Responsive: on phones the panels stack below the board.

**Steps:**
- [ ] **Step 1.** Write the model tests with real engine states from scripted games:
  - `decisionFor` covers every decision kind, and each submission is in `legal`.
  - Hand classification matches `classifyTile`.
  - Chain prices match the engine's pricing.
- [ ] **Step 2.** Implement. Run `pnpm check`. Commit "Add Chain Reaction game screen".

### Task 6: End-to-end browser test, docs and deployment

- `docs/PLAN.md`
- `README.md`: how to run, test and play
- `docs/TESTING.md`: the owner's morning test guide

**The e2e test:**
- Start the dev relay and `vite preview`.
- Open three browser contexts with profiles `a`, `b` and `c`:
  - `a` creates a 3-seat table with 2 open seats
  - `b` and `c` join from the share link
  - `a` starts the game
- All three reach the play phase.
- The pending player places a tile through the UI, and the other contexts see it.
- Play continues for at least 2 full rounds, by clicking the first legal option in each decision.

Use `executablePath: '/opt/pw-browsers/chromium'` if the pinned Playwright version differs.
